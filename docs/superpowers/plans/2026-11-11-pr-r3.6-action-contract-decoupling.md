# PR-R3.6 Action Contract Decoupling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Agent-facing Action Contract genuinely independent of MCP, Controller and platform Driver implementations, and make `ActionReceipt` part of the production execution path rather than an unused DTO.

**Architecture:** Introduce a platform-neutral L3 `ActionService` and `ActionDispatchPort`. Agents call `ActionService.execute(...)`; the service lowers the agent action dialect into an `ActionCommand`, calls an injected L4 implementation of `ActionDispatchPort`, and returns a `ToolExecutionResult` plus `ActionReceipt`/effect evidence. MCP and Controller code become L1/L4 adapters behind the port. No compatibility dependency is added to the architecture allowlist.

**Tech Stack:** Python 3.12, pytest, dataclasses, `Protocol`, existing `core/actions.py`, `ActionSession`/MCP transport, AST-based import graph tests.

**Spec:** PR-R3.6 owner requirements plus `docs/SHOWCASE_RESULT-20261111-3.md` (R3.2/R3.3) and `docs/architecture/ARCHITECTURE_CONTRACT.md`.

## Global Constraints

- Do not add any entry to `tests/unit/architecture/legacy_allowlist.py`. The target is zero legacy entries.
- `artemis.agents.*` must not import, directly or transitively, `artemis.mcp`, `artemis.controllers`, `artemis.drivers`, or `artemis.adapters`.
- `artemis.actions.*` must not import `artemis.agents.*`, `artemis.mcp.*`, `artemis.controllers.*`, `artemis.drivers.*`, or `artemis.adapters.*`.
- `artemis.actions.*` may import `artemis.core.*`, plus pure Python/stdlib and the shared `ActionSession` only through an injected protocol, never by constructing an MCP server.
- `artemis.perception`, `artemis.control`, `artemis.safety` may not build hardware Adapters or import MCP.
- Keep the public `McpActionExecutor`/MCP tool surface as a compatibility facade; do not change MCP tool schemas.
- `ActionResult.ok` remains "adapter accepted/dispatched"; it never means observed effect or goal verification.
- `ActionReceipt.state` must be written by the production execution path. Post-effect evidence may be an `ActionState.OBSERVED_EFFECT` transition and `ActionEvidence.action_state`, but only with an explicit evidence source.
- The architecture test must scan static imports, literal dynamic imports, and transitive module dependencies.
- Every task ends with focused tests and a commit. Do not run a broad refactor without a test gate.

## Review Focus

- An Agent can reach MCP through `actions.service -> actions.session -> mcp.action_server` even when the direct agents→mcp graph is clean; the transitive graph must fail this path.
- Lazy `importlib.import_module("artemis.mcp...")` calls inside helpers must be detected, not hidden from the static scanner.
- `ToolExecutionResult` imported from `agents.validator.tool_declarations` into `actions.executor` is a reverse L3→L2 dependency; moving the class must retain the old import path as a shim for agents/tests during migration.
- A compatibility `McpActionExecutor` must not be constructible by Agent code; only the MCP/CLI integration layer may choose it.
- `ActionReceipt` must not be populated only in tests; production `ActionService.execute()` must create and return it.
- `ActionSession` closing/error behavior must remain MCP-compatible even after moving the transport behind the port.
