# PR-R3.5 Flash Safety Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the remaining Flash batch-action safety bypasses so `click_sequence`, actual click counts, stale observations, and high-value effects cannot be reported as verified without evidence.

**Architecture:** Keep the existing L3 risk policy in `artemis/safety/flash.py` as the single policy source. The Flash runner computes a `FlashActionCost` from each tool invocation, gates the whole batch before dispatch, and only promotes an action receipt after observed-effect or post-verification evidence. No change to the Action Specs/MCP schema or to `ActionResult.ok` semantics.

**Tech Stack:** Python 3.12, pytest, dataclasses, existing `ToolExecutionResult`/`FlashActionPolicy`/`FlashPrecondition`/`ActionEvidence` contracts.

**Spec:** `docs/SHOWCASE_RESULT-20261111-3.md` (P1-2/P1-4 and R3.2), together with the PR-R3.5 requirements supplied by the owner.

## Global Constraints

- Scope is limited to `artemis/safety/flash.py`, `artemis/agents/flash/runner.py`, and the two listed test files; update any pre-existing test fixtures required by this contract change in the same task.
- `click_sequence` is one tool call but may represent many real clicks. Its `sequence` length is the click count.
- `click(times=N)` is one tool call but N real clicks. `times` defaults to 1.
- Budget values for this PR: `MAX_FLASH_ACTIONS_PER_TURN = 8`, `MAX_FLASH_CLICKS_PER_TURN = 3`, `MAX_FLASH_RISK_UNITS = 6`.
- High-risk actions cost 2 risk units per click; normal actions cost 1. A `click_sequence` of 10 costs 20 risk units and 10 clicks, and must be rejected before dispatch.
- `verify_after` remains the explicit pixel-verification opt-in. High-value actions may satisfy the effect requirement through the existing no-op dHash evidence instead; missing evidence must not become `observed_effect` or `verified_*`.
- Do not change `ActionResult.ok` semantics: it still means the adapter accepted/dispatched the action.
- Do not add a second platform branch in Agent code. Policy lives in L3 `safety/flash.py`.
- Every task ends with focused tests and a commit. Run the full suite once at the end.

## Review Focus

- A 10-entry `click_sequence` must be rejected as **one** tool call, with no actuator dispatch.
- `click(times=4)` and a cumulative `1 click + 3-entry sequence` must be rejected by the click/risk budget, not by the old 8/2 tool-call count.
- A stale observation must reject a `click_sequence` before any of its points are sent.
- A high-value action with only an ACK and no effect evidence must be `unknown`/`target_unverified`, never `observed_effect` or `verified_success`.
- A failed explicit `verify_after` must leave the action failed, not upgrade it to a successful receipt.

In `FlashRunner._process_tool_calls`:

1. Compute `cost = flash_action_cost(name, args)` for every `name in action_names`.
2. Increment prospective counters: `next_clicks = burst_clicks + cost.clicks`, `next_risk = burst_risk_units + cost.risk_units`.
3. Call `burst_budget.allows(name, burst_position, clicks=next_clicks, risk_units=next_risk)`.
4. On rejection, emit an error `ToolMessage`, append the error to `turn.actions`, and `continue` without calling `_execute_and_record_action`.
5. Only update counters after the action is allowed. Do not count helper tools such as `ask_explorer`.
6. Keep the distinct error text for:
   - action not in allowlist,
   - click cap exceeded,
   - risk-unit cap exceeded,
   - total action cap exceeded.
