# iOS UVC P5: Validator Consumes Structured Tap Incidents

> **REQUIRED SUB-SKILL:** superpowers:executing-plans.

**Goal:** Make the iOS relative-HID tap result (`pointer_missing` / `pointer_off_target` /
`pointer_not_centered` / `no_effect`) reach the Validator, the incident record, and the
Operator prompt, without changing Android behavior.

**Architecture:** The incident is produced by `SessionTapController` → `HidControlSink` →
`IOSUvcHidDriver`, carried up the existing single choke point (`UnifiedMobileController.tap_at`
→ `AdbActuator` → MCP `ActionResult`), and consumed by `Validator._exec_action`, which records
it on the action item and maps it to a `ValidationErrorCategory`. No platform branch anywhere.

**Spec:** `docs/ios-uvc-execution-plan.md` Phase P4 (IOS-UVC-41..45) and
`docs/ios-artemis-fusion-status.md` §5 P5.

## Global Constraints

- Core orchestration branches on capabilities, never on `platform == "ios"`.
- Android behavior and Android tests must not change.
- A tap with no verified pointer must never click; the incident says why.
- Failures are incidents, never silent successes.

## Review Focus

- An Android driver returns `ActionResult` with no incident — every new field must default to
  `None` so old payloads decode.
- A burst (2+ actions) must still abort on the first failed action and not retry.
- The incident record must stay JSON-serializable (no dataclasses, no PIL objects).
- `action_item` copies into traces: the new enrichment must not bloat records or leak into the
  Operator-facing action dict.
- Retry policy: the controller already performed its bounded correction loop; the Validator
  must not multiply UVC grabs by retrying a pointer incident.
