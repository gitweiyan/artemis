# R3.6 Task 2 — Action Service / Action Port Completion Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `ActionService` the semantic owner of device actions and make `ActionDispatchPort` a real `ActionCommand → ActionDispatchResult/ActionReceipt` boundary, with MCP reduced to an adapter.

**Architecture:** Keep the existing `DeviceActionService` translation logic as the starting point, but make it produce an `ActionCommand` and call the injected port. `ActionService` owns receipt creation, observation, effect evidence, and `ToolExecutionResult`. `McpActionPort` is an L1 adapter over `ActionSession`; `McpActionExecutor` remains only a compatibility facade for helper tools and old tests.

**Tech Stack:** Python 3.12, pytest, dataclasses, Protocol, existing `core.actions`, `ActionSession`, MCP FastMCP.

**Spec:** `docs/superpowers/plans/2026-11-11-pr-r3.6-action-contract-decoupling.md` (Task 2 acceptance), plus the owner's Task 2 acceptance criteria.

## Global Constraints

- Do not add entries to `tests/unit/architecture/legacy_allowlist.py`.
- `artemis.actions` must not import `artemis.mcp`, `artemis.agents`, `artemis.controllers`, `artemis.drivers`, or `artemis.adapters` (direct or transitive).
- `ActionDispatchPort.dispatch()` must consume `ActionCommand` and return a receipt-bearing result; it must not be an `execute(name,args,...)` wrapper.
- `ActionService` must not construct a controller, actuator, MCP server, or `ActionSession`.
- `ActionResult.ok` remains adapter ACK only. Receipt promotion to `observed_effect` requires explicit effect evidence.
- Keep MCP tool schemas and `McpActionExecutor` import paths working for compatibility.
- Every task has a RED test first, a focused GREEN run, and a commit.
- Run the full suite and quality ratchet once after Task 4.

## Review Focus

- A fake port must receive a fully translated `ActionCommand`; if it receives the raw agent args, the service is still a wrapper.
- `click_sequence` must remain one command with its sequence intact, not be split or coerced into a single click.
- A failed port dispatch must produce `UNKNOWN`/`REJECTED`, never a verified state.
- `ActionService` must not fall back to `McpActionExecutor.execute` for a device action after the port migration.
- Helper tools must still work when only the compatibility executor is present.
- Composition must attach the service after the device session exists, without reviving the factory recursion bug.

```python
@dataclass(frozen=True)
class ActionDispatchResult:
    receipt: ActionReceipt
    result: ActionResult

@runtime_checkable
class ActionDispatchPort(Protocol):
    async def dispatch(self, command: ActionCommand) -> ActionDispatchResult: ...
    async def observe(self, settle_ms: int = 400, include_image: bool = False) -> Any: ...
    async def close(self) -> None: ...
```

- [ ] **Step 3: Implement the adapter and composition**

- `McpActionPort` owns no translation; it only calls the session with
  `command.adapter_id` / `command.parameters`.
- `observe` delegates to `session.observe`.
- `ActionService` in `interfaces/action_bootstrap.py` is constructed with
  `ctx`, `McpActionPort`, and a helper executor for non-device tools.

  action execution should delegate to `ActionService` or remain explicitly
  deprecated, not be the production path.
- Do not attach the service inside `drivers.factory`; composition stays outside
  the driver builder to avoid recursion.
